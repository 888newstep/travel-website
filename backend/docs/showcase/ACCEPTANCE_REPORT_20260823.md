## 4. 本轮根因修复

### 4.1 问题

收藏服务原先通过公开路线详情接口校验路线。公开详情会同步原子增加浏览量、插入 `route_visit` 并清理缓存；在 100 并发首个请求中，这条跨服务调用超过 Feign 3 秒读取超时，收藏服务把超时错误折叠为“路线不存在”404。

### 4.2 方案比较

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| 只增加 Feign 超时 | 修改快 | 掩盖副作用接口设计，延迟继续随统计链路增长 | 不采用 |
| 收藏服务直接读路线表 | 延迟低 | 破坏微服务数据边界，形成跨服务数据库耦合 | 不采用 |
| 新增认证的无副作用读取契约 | 保持权限语义和服务边界，不污染统计 | 增加一个明确的内部业务契约 | 采用 |

### 4.3 实现

- 路线服务新增 `GET /routes/{id}/readable`，复用公开/所有者可读规则，但不记录访问统计。
- 收藏服务 Feign 统一改用该接口，因此收藏、评论和分享的路线读取都不再触发访问副作用。
- 新增控制器和 Feign 包装测试，证明公开详情仍记录访问、业务读取不记录访问。

## 5. 面试讲述建议

推荐按“问题—风险—取舍—证据”回答：

> 我没有通过增加 Feign 超时掩盖并发失败，而是发现服务间存在性校验错误复用了带访问统计副作用的公开详情接口。最终拆出认证的无副作用读取契约，保留公开详情的 PV/UV 语义，再用 100 线程 JMeter 证明 1 次执行、99 次处理中冲突、数据库唯一且自动恢复基线。

可继续追问的技术点：

- 为什么幂等选择 Redis 状态机加数据库唯一键，而不是只用分布式锁。
- 为什么 Redis 故障选择 503 fail-closed，而不是跳过幂等继续写。
- 为什么服务间查询也要保持用户可见性权限，而不是只判断主键存在。
- 为什么访问统计保存加盐哈希而不保存原始 IP/User-Agent。
- 为什么 RabbitMQ 只承诺最终一致性，不承诺跨服务强一致事务。

## 6. 剩余风险与后续优先级

1. 当前并发场景 P95 约 3.4 秒，正确性已通过，但仍应继续拆分用户校验、缓存失效和数据库写入耗时。
2. Feign 包装层仍把部分依赖异常转换为空值，后续应区分 404、403、超时和服务不可用，避免错误语义折叠。
3. 全栈 E2E 目前以脚本和本地依赖为主，后续可接入 CI 的容器化 MySQL/Redis，并把云 RabbitMQ/高德放到受控的手工验收任务。
4. 演示数据库存在重复历史路线种子，不影响当前验收，但应在正式演示前执行一次数据整理，避免列表噪声。
